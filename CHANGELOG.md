# Changelog

## [0.5.0]
### Added
- **`EnumConfigField`**: a field holding any enum, with no class to write per enum. The enum is a setting of the field (`SetEnumType`, or typed in the inspector), stored as `"Namespace.Outer+Nested, Assembly"`. The value is stored as the **name** of the option, never its number, so renumbering an enum does not change what was saved; a `[Flags]` enum is stored as the names joined by ", ". The string is canonical (`"air,  ground"` is kept as `"Ground, Air"`), so saved files and `StringValueEquals` are stable. Strings that are not an option (a number, an unknown name, a bad part of a flags list) are not accepted: `SetStringValue` returns false, and a bad value in a saved file leaves the field at its default. With no type set, or one that can't be found any more (the enum was renamed or removed), the field accepts any string, so no value is lost, and the inspector says so.
  - It derives from `StringConfigField`, so everything that takes a string field takes this one: the storages, `StringConfigReader`, `ConfigGuiSwitch` and `ConfigGuiSwitchSlider`.
  - Typed access for code: `TryGetValue<TEnum>`, `GetValue<TEnum>`, `SetValue<TEnum>` (an error if the field is of another enum) and `Subscribe<TEnum>(callback, invokeNow)`, whose result is disposed to stop. Static helpers `TryParseValue`, `IsActive`, `SetFlag`, `ResolveType`, `FormatTypeName` serve the readers and editors.
  - The debug GUI shows a list of buttons, one per option (the current one pressed), or a list of toggles for flags. A row of a list of fields is one line: a button that moves on to the next option, or just the text for flags.
- **`EnumConfigReader`**: passes the value on as the enum itself, whatever the enum (a `UnityEvent` can't carry one). `Bindings` write it by reflection to a field or property of the right type of any component or ScriptableObject (chosen from a popup of the members that fit); `Options` are `UnityEvent<bool>`s, one per option name, called with true when the option becomes the value and false when it stops being (of a flags enum: when the flag is contained in the value; the option 0 is on only for 0), and once at the start with the state then. Members reached only by reflection can be stripped by IL2CPP (a property that nothing else uses: add `[Preserve]`).
- **`ConfigGuiEnumSwitch` and `ConfigGuiEnumSwitchSlider`**, the uGUI elements for an `EnumConfigField`, next to `ConfigGuiSwitch` and `ConfigGuiSwitchSlider` (which take any string). Their options are chosen from a popup of the names of the field's enum instead of being typed, and a value that is not an option is never written. The switch is one toggle per option, one on at a time; for a `[Flags]` enum each toggle is a flag, and any number can be on. The slider goes through the options in the order they are listed (not for flags: it warns). They live with the options drawers in a new editor assembly, `SeweralIdeas.ConfigGui.Editor`, compiled where uGUI and IMGUI are present.
- A game object dropped on the target of a binding of the `EnumConfigReader` is replaced by the component that has the member: at once if there is one, otherwise the one chosen from a popup.
- `ConfigListener` has a protected `Field` property for the field it listens to.
- The inspector of an `EnumConfigField` picks the enum type in a popup window: a search box (Enter picks the first match, Escape closes) over the list of the enums whose name contains the text. The default value is a list of buttons, one per option (toggles for flags).
- `ConfigFieldEditor.DrawFields` is overridable, to draw the properties of a field differently.
- Edit mode tests (`Tests/Editor`).

### Fixed
- `ConfigGuiSwitch` never removed its listeners from the toggles: it added them again on every `OnEnable`, so a switch that was disabled and enabled again (a menu that is shown and hidden) called `OnToggle` several times per click. It removes them in `OnDisable` now.

### Changed
- **The text format (the file storage and the single-string PlayerPrefs storage) writes a string in quotes, and reads a quoted value as it is.** `name = "Hello World"` instead of `name = Hello\_World`; a number or a bool is written without quotes, as before. A value that starts with a quote is read verbatim up to the closing quote, spaces and `=` included; `\"` is a quote, `\\` a backslash, `\n` and `\r` the line breaks, and a backslash before anything else stays a backslash (a path can be written as it is). A quoted value can go over several lines (Windows line endings are read as `\n`), and only spaces may follow the closing quote. A value that does not start with a quote is read as before: unescaped spaces are ignored (also around the `=`), `\_` is a space, `\=`, `\n` and `\\` the other escapes. Quotes elsewhere in an unquoted value are just characters.
- A second `=` in an unquoted value is part of the value (it used to start the key over). A `\r` outside quotes is ignored, so a file with Windows line endings reads the same.
- A string field that holds nothing (null) is written as an empty string.

### Breaking changes
- **Files written by this version cannot be read by 0.4.0 and older**: they take the quotes for part of the value (and drop its spaces). Files written by older versions read as before. Upgrade: nothing, the next save rewrites the file in the new form.

An enum option renamed in code makes the name saved for it invalid: it loads as the default.

## [0.4.0]
### Changed
- **Config no longer depends on UnityUtils**, in its runtime or its editor: no asmdef of Config references another seweralideas assembly. The delayed text field of the numeric and string fields is an internal copy (`DelayedText`), and the editors pick a type to add with their own `GenericMenu` list (`TypeMenu`) in place of UnityUtils' `TypeDropdown` (no icons, no search).
- **The IMGUI parts need the built-in IMGUI module.** `ConfigField.GetGUIHeight` / `OnConfigGUI` / `GetRowHeight` / `OnConfigRowGUI` (and their overrides) and `ConfigDebugGUI` are compiled only where `com.unity.modules.imgui` is enabled (the asmdef sets `SEWERALIDEAS_CONFIG_IMGUI`). The editor assembly (`SeweralIdeas.Config.Editor`) needs it too, as it draws them.
- `ConfigGuiSlider` / `ConfigGuiIntSlider` can write their text straight to a `TMP_Text` (a new optional field, `m_tmpOutput`), through `TMP_Text.SetText(StringBuilder)`: the number is formatted into a stack buffer and a reused `StringBuilder`, so showing a value allocates no string. It exists where TextMeshPro is (`com.unity.ugui` 2.0+ or `com.unity.textmeshpro`; the asmdef sets `SEWERALIDEAS_CONFIG_TMP`). A new public `TextChanged` event adds and removes its listeners on `m_textOutput`, so code and the inspector share one `UnityEvent<string>`; the string is built only if something listens (a `UnityEvent` counts only the inspector's listeners, so `TextChanged` counts the others itself - subscribe through it, not through `AddListener`). The two sliders share this in a new base class, `ConfigGuiTextElement<T, TField>`.
- The sliders format with an internal `ValueFormat` (a composite format string with one number, `"{0:F2} dB"`), no longer UnityUtils' `CachedStringFormatter`. The format strings behave the same, except that a format item has no alignment (`{0,5}`) and `{0}` is the only argument. The text is no longer cached between identical values.
- **`SeweralIdeas.ConfigGui` (the uGUI components) needs both uGUI and IMGUI**, and is only compiled where `com.unity.ugui` and the IMGUI module are present. It references `UnityEngine.UI` explicitly.

Upgrade: nothing in a project with the default modules. A project with the IMGUI module disabled loses `ConfigDebugGUI`, the `OnConfigGUI` family and the Config inspectors.

## [0.3.0]
### Added
- A "Show" button next to Load and Save in the `Config` inspector: it opens the file of a file storage in the file browser (or the nearest folder that exists, as the file is made when the config is saved), and, for the PlayerPrefs storages, the PlayerPrefs of the editor - in regedit at the key of the project on Windows, and the plist or prefs file in the file browser on macOS and Linux. Each storage does it itself, in an editor-only (`#if UNITY_EDITOR`) abstract `ConfigStorage.RevealInEditor(config)`, which a custom storage has to implement; `Config.RevealStorageInEditor()` calls the one of the storage that is available. Regedit opens at the last key it showed, so one that is already open stays where it is.
- `ConfigField.GetRowHeight` / `OnConfigRowGUI`: the value as shown in a list of fields, by default the same as `GetGUIHeight` / `OnConfigGUI`. A `StringConfigField` is one line there (editable if the text is one line, otherwise its first line, to be edited in the field's own inspector), so a string no longer makes the table of a config eight lines tall.
- `ConfigEditor` shows the fields of a config as a table of their current values, editable in place, and live while the game runs; the rows can be dragged to reorder the fields (which is the order of the debug GUI), "+" creates a field as a nested asset and "-" removes the selected one. "Unsaved changes" shows when there are any. The selected field is edited below the table (its name, and its default value).
- `PlayerPrefsBlobStorageDescription` / `PlayerPrefsBlobStorage`: a config stored as a single PlayerPrefs string under its global name, in the text format of the file storage. It sits next to the per-field `PlayerPrefsStorageDescription` (one key per field, now prefixed by the global name), and a plan can use either. One key per config means a removed or renamed field leaves nothing behind (PlayerPrefs cannot list or delete keys it does not know), and the fields are saved together; the values cannot be read one by one with PlayerPrefs. Make it with Create > SeweralIdeas > Config > PlayerPrefsBlobStorageDescription.
- `ConfigStoragePlan` has an editor for its descriptions: a list in the order they are tried, which can be dragged to change it. "+" opens a type dropdown and creates the description as a nested asset of the plan (at the end of the list); "-" removes the selected entry, and destroys the description too if it is nested in this plan (a description asset that was merely listed stays). The selected description is edited below the list.

### Breaking changes
- **`PlayerPrefsStorage` stores an `int`, `float` or `bool` field as such (a bool as 0 or 1) and any other field as a string**, under keys that have the config's global name in front (`GlobalName/fieldName`), so two configs with a field of the same name no longer share a value. A config without a global name keeps the bare field name. Values saved under the old keys are not read: the fields start from their defaults, and the old keys stay in PlayerPrefs. Upgrade: save once under the new name, or copy the old keys over by hand.
- PlayerPrefs does not remember what type a key was stored as, and reading it as another type gives the default of that type: a field whose type changes (an int that becomes a float, say) reads as if it had no value, and takes its default.
- `ConfigStorage.LoadField` takes the `Config` as its first parameter (`LoadField(Config config, string key, ConfigField field)`); custom storages have to take it.
- **`StorageDescription` is a ScriptableObject** (it was a `[Serializable]` class held by `[SerializeReference]`). A `ConfigStoragePlan` lists the description assets, in order of preference; make them with Create > SeweralIdeas > Config > `PlayerPrefsStorageDescription` or `FileConfigStorageDescription`. The type names stored in the plan are no longer a risk (renaming a description class used to break the plan), and the `[Preserve]` attributes are gone. Upgrade: a plan that had descriptions in its list has to be given description assets; the old entries are lost when the plan is next loaded. `FileConfigStorageDescription` and `PlayerPrefsStorageDescription` are in files of their own now (an asset needs its class in a file of the same name).
- The `SeweralIdeas.Config` assembly no longer references `SeweralIdeas.Drawers` (`[InstantiateGUI]` was the only use), and `Config.m_storagePlan` is a plain serialized reference (it had a stray `[SerializeReference]`; the data is the same).

### Fixed
- `FloatConfigField` saved its value as text with `ToString()`, which can keep fewer digits than a float needs, so a value saved to a file (or the single-string PlayerPrefs storage) could change a little each time it was saved and loaded. It uses the round-trip format now. The per-field PlayerPrefs storage keeps floats as floats.
- `ConfigEditor` re-enabled the whole GUI after the Load and Save buttons (it set `GUI.enabled` to `true` afterwards), and kept the state of the "Fields" foldout in another property's expanded flag; neither is the case any more.
- Reading a damaged file (or PlayerPrefs string) in the text format threw out of `Load`, on an unknown escape or a repeated key. It is logged now, none of the damaged data is used, every field gets its default and the next save replaces it.
- **Without the domain reload on entering play mode, a play session started with the runtime state of the last one**: field values, the listeners of destroyed objects, a dirty flag. Each session now starts by resetting the loaded configs and their fields to what a freshly loaded asset has (and loading the auto-loading ones again), when the domain reload is switched off; with it on, the reload does that already.
- A `Config` left its handler on the static `Application.quitting` event when disabled; it unhooks it now.
- `Save()` and `Load()` threw when no storage was available (and `Save()` runs when quitting with auto-save on). They warn instead: `Save()` stays dirty, and `Load()` gives every field its default value.
- Editing a `ConfigField` sub-asset selected on its own (in the Project window) never reached the asset: `ConfigFieldEditor` didn't apply the changes of its serialized properties (the default value, say). It does now. Edited inside the `Config` inspector it worked only because that applied them.
- Removing a field from a `Config` left an empty entry in its list (deleting an array element that holds an object only clears it), which broke `Load` and the field list. The entry is removed now, the selection stays valid, and the empty entries already left behind are dropped when the config validates and skipped when it loads.
- Renaming a field didn't mark the sub-asset dirty, so the new name wasn't saved. Names are the storage keys, so a rename to a name that another field of the config has is refused, and new fields get a unique name (`FloatConfigField`, `FloatConfigField 1`, ...).
- Creating and removing a field is one undo step (it was several), and creating one on a config that isn't an asset is refused with an error.
- `ConfigEditor` created a new editor for the selected field on every repaint and never destroyed it; it keeps one now.
