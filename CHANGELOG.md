# Changelog

## [0.3.0]
### Added
- A "Show" button next to Load and Save in the `Config` inspector: it opens the file of a file storage in the file browser (or the nearest folder that exists, as the file is made when the config is saved), and, for the PlayerPrefs storages, the PlayerPrefs of the editor - in regedit at the key of the project on Windows, and the plist or prefs file in the file browser on macOS and Linux. Each storage does it itself, in an editor-only (`#if UNITY_EDITOR`) abstract `ConfigStorage.RevealInEditor(config)`, which a custom storage has to implement; `Config.RevealStorageInEditor()` calls the one of the storage that is available. Regedit opens at the last key it showed, so one that is already open stays where it is.
- `ConfigField.GetRowHeight` / `OnConfigRowGUI`: the value as shown in a list of fields, by default the same as `GetGUIHeight` / `OnConfigGUI`. A `StringConfigField` is one line there (editable if the text is one line, otherwise its first line, to be edited in the field's own inspector), so a string no longer makes the table of a config eight lines tall.
- `ConfigEditor` shows the fields of a config as a table of their current values, editable in place, and live while the game runs; the rows can be dragged to reorder the fields (which is the order of the debug GUI), "+" creates a field as a nested asset and "-" removes the selected one. "Unsaved changes" shows when there are any. The selected field is edited below the table (its name, and its default value).
- `PlayerPrefsBlobStorageDescription` / `PlayerPrefsBlobStorage`: a config stored as a single PlayerPrefs string under its global name, in the text format of the file storage. It sits next to the per-field `PlayerPrefsStorageDescription` (one key per field, now prefixed by the global name), and a plan can use either. One key per config means a removed or renamed field leaves nothing behind (PlayerPrefs cannot list or delete keys it does not know), and the fields are saved together; the values cannot be read one by one with PlayerPrefs. Make it with Create > SeweralIdeas > Config > PlayerPrefsBlobStorageDescription.
- `ConfigStoragePlan` has an editor for its descriptions: a list in the order they are tried, which can be dragged to change it. "+" opens a type dropdown and creates the description as a nested asset of the plan (at the end of the list); "-" removes the selected entry, and destroys the description too if it is nested in this plan (a description asset that was merely listed stays). The selected description is edited below the list.

### Breaking changes
- **`PlayerPrefsStorage` stores an `int`, `float` or `bool` field as such (a bool as 0 or 1) and any other field as a string**, under keys that have the config's global name in front (`GlobalName/fieldName`), so two configs with a field of the same name no longer share a value. A config without a global name keeps the bare field name. Values saved under the old keys are not read: the fields start from their defaults, and the old keys stay in PlayerPrefs. Upgrade: save once under the new name, or copy the old keys over by hand.
- PlayerPrefs does not remember what type a key was stored as, and reading it as another type gives the default of that type: a field whose type changes (an int that becomes a float, say) reads as if it had no value, and takes its default.
- `ConfigStorage.LoadField` takes the `Config` as its first parameter (`LoadField(Config config, string key, ConfigField field)`); custom storages have to take it.
- **`StorageDescription` is a ScriptableObject** (it was a `[Serializable]` class held by `[SerializeReference]`). A `ConfigStoragePlan` lists the description assets, in order of preference; make them with Create > SeweralIdeas > Config > `PlayerPrefsStorageDescription` or `FileConfigStorageDescription`. The type names stored in the plan are no longer a risk (renaming a description class used to break the plan), and the `[Preserve]` attributes are gone. Upgrade: a plan that had descriptions in its list has to be given description assets; the old entries are lost when the plan is next loaded. `FileConfigStorageDescription` and `PlayerPrefsStorageDescription` are in files of their own now (an asset needs its class in a file of the same name).
- The `SeweralIdeas.Config` assembly no longer references `SeweralIdeas.Drawers` (`[InstantiateGUI]` was the only use), and `Config.m_storagePlan` is a plain serialized reference (it had a stray `[SerializeReference]`; the data is the same).

### Fixed
- `FloatConfigField` saved its value as text with `ToString()`, which can keep fewer digits than a float needs, so a value saved to a file (or the single-string PlayerPrefs storage) could change a little each time it was saved and loaded. It uses the round-trip format now. The per-field PlayerPrefs storage keeps floats as floats.
- `ConfigEditor` re-enabled the whole GUI after the Load and Save buttons (it set `GUI.enabled` to `true` afterwards), and kept the state of the "Fields" foldout in another property's expanded flag; neither is the case any more.
- Reading a damaged file (or PlayerPrefs string) in the text format threw out of `Load`, on an unknown escape or a repeated key. It is logged now, none of the damaged data is used, every field gets its default and the next save replaces it.
- **Without the domain reload on entering play mode, a play session started with the runtime state of the last one**: field values, the listeners of destroyed objects, a dirty flag. Each session now starts by resetting the loaded configs and their fields to what a freshly loaded asset has (and loading the auto-loading ones again), when the domain reload is switched off; with it on, the reload does that already.
- A `Config` left its handler on the static `Application.quitting` event when disabled; it unhooks it now.
- `Save()` and `Load()` threw when no storage was available (and `Save()` runs when quitting with auto-save on). They warn instead: `Save()` stays dirty, and `Load()` gives every field its default value.
- Editing a `ConfigField` sub-asset selected on its own (in the Project window) never reached the asset: `ConfigFieldEditor` didn't apply the changes of its serialized properties (the default value, say). It does now. Edited inside the `Config` inspector it worked only because that applied them.
- Removing a field from a `Config` left an empty entry in its list (deleting an array element that holds an object only clears it), which broke `Load` and the field list. The entry is removed now, the selection stays valid, and the empty entries already left behind are dropped when the config validates and skipped when it loads.
- Renaming a field didn't mark the sub-asset dirty, so the new name wasn't saved. Names are the storage keys, so a rename to a name that another field of the config has is refused, and new fields get a unique name (`FloatConfigField`, `FloatConfigField 1`, ...).
- Creating and removing a field is one undo step (it was several), and creating one on a config that isn't an asset is refused with an error.
- `ConfigEditor` created a new editor for the selected field on every repaint and never destroyed it; it keeps one now.
